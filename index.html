Trade-offs
  • Hybrid over dense-only: dense search catches paraphrases, BM25 catches exact terms such as error codes, and rank fusion merges both without calibrating their scores.
  • The BM25 index lives in memory and is rebuilt from Qdrant at startup, which keeps the code small but ties it to one process.
Where it breaks
  • The 47 of 50 comes from an easy corpus built from the test set's own passages.
  • A hit is a string match on 60 characters, and citation presence checks the format, not whether the source supports the claim.
  • No LLM-judge (RAGAs) run is committed, and CI does not run the eval.
  • No auth, and uploading a file twice indexes it twice.

LLM Gateway
Tracks and prices every AI call from the provider's own token counts.
$0.00005 cost of one real call, logged

  
Problem
A live app makes LLM calls on a free tier. Each call needs a trace and a cost that holds up, without guessing token counts from string length.
How it works
  1. App/v1/chat or /stream
  2. Guardbearer key, size limits, model allow-list
  3. ProviderGroq or Gemini
  4. Priceprovider tokens × dated list price
  5. RecordLangfuse trace + SQLite ledger
Evidence

FastAPILangfuseSQLiteDocker
Run it
llm-gateway
real output, captured 2026-11-26 from a fresh clone
Trade-offs
  • Costs are paid-tier list prices with a source URL per entry. On Groq's free tier the real bill is 0; the figure is what the same traffic would cost at scale.
  • With no Langfuse keys it runs a no-op tracer and returns trace_id: null rather than a fake id.
  • The caller sends a hashed user id, so raw emails never reach the gateway.
Where it breaks
  • One provider per process: if Groq is down, calls fail. Nothing falls back to Gemini.
  • Gemini answers arrive as one chunk, not a real stream.
  • A stream that fails halfway leaves no ledger row, so its tokens go uncounted.
  • One SQLite file, one instance. Added latency is not measured yet.

Deutsch-Tutor
AI German tutor that builds your curriculum from your own mistakes.
Live tutor.aravindpradee.me

  
Problem
Built to practise my own German at B1 in Cottbus. A chat model forgets your mistakes; this app logs every one and turns them into drills.
Every error you make in live conversation is logged and turned into drills: the reply streams immediately while a parallel corrector marks exact error spans, and a decay-weighted formula, not an LLM, picks what you practice next.
How it works
  1. You writeA1 to B2
  2. Tutorstreams a German reply over SSE
  3. Correctorin parallel: JSON with exact error spans
  4. Logdrills + spaced repetition
  5. Next focusa formula, not an LLM

Trade-offs
  • Corrections are best effort and never block the reply: the conversation is the product.
  • Error spans must be exact substrings, enforced in code, because the UI highlights by match and a paraphrased span would show nothing.
  • A decay-weighted formula picks what to practise next: explainable, free and testable, but it only ranks four coarse error types.
Where it breaks
  • Corrector quality is not measured: no labelled set, no precision or recall.
  • The chat and correction routes have no rate limit; cost control relies on the provider's free tier.
  • Tests exist but no CI runs them. The conversation keeps only the last 10 messages.
